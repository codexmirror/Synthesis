## Product foundation

Synthesis currently runs as a responsive browser-based NODE-OS prototype.

The application uses a freshly created, versioned, sliced in-memory `GameState`
for each client session.

No save or migration system is implemented.

NODE-OS Home is a compact two-column technical control surface exposing these
player-facing applications in order:

- Terminal
- NodeScan
- NodeMail
- Processes
- Files
- Market
- Wallet
- Notes
- System

These applications describe the current interface and are not a permanent
product taxonomy. Shell navigation is presentation state rather than gameplay
state, and the applications share one NODE-OS presentation language rather than
each owning a private one.

Mobile Safari/iPhone is a current first-class presentation target, using the
established Shell-owned Editing presentation.

Details: [`current/INTERFACE_SHELL.md`](current/INTERFACE_SHELL.md).


## Represented world

Current canonical game state includes the player's local Device, two
independent canonical economic domains (the Civic Dollar Provider and NODE), the represented
World, the player's in-world mailbox, and the Process, Knowledge, Discovery,
DeviceAccess, RemoteSession and FileTransfer slices.

The World currently contains the `home-net` LocalNetwork, the player's local
Device (`node-01`) and fully interactive LAN server `srv-01`, plus remote `srv-02` at `203.0.113.42`. `srv-01` provides the GateSSH 1.3.2 tutorial access path and a downloadable concrete GateSSH package. `srv-02` begins with patched GateSSH 1.3.3 and public RackUpdate 1.0: observing and analyzing the update surface, attacking RackUpdate's rollback weakness with Flipper's integrated Rollback Module, submitting the local 1.3.2 package through the resulting narrow submission capability, then re-analyzing GateSSH composes a real state-changing interaction with the existing credential technique. Neither the attack nor the submission grants access; both are represented finite work, and a successful submission legitimately refreshes only the fingerprint it applied.

## Reconnaissance, knowledge, and access

The current investigation loop, as represented operations, is:

```text
scan SELF
↓
discover home-net
↓
scan home-net
↓
discover a LAN server
↓
scan that server
↓
discover represented services
↓
analyze a service → vulnerability Knowledge
↓
attack that service → DeviceAccess
↓
connect → Remote Session → the target's own operating surface
```

Which surface that is comes from the entered Device's represented Firmware
identity: a RACK-OS server mounts RACK-OS, and the one represented personal
phone mounts VEYRA OS. Firmware with no implemented surface mounts none.

The player expresses that loop through NodeScan as three actions — SCAN, HACK
and CONNECT — over Known Space, and one target at a time. The represented
operations underneath are unchanged, and Terminal still exposes each of them
individually.

NodeScan is the single player-facing home for network space. Known Space is a
compact expandable tree — Network → Device — whose roots are both the
Networks the local Device legitimately manages and the Networks
reconnaissance remembers. A Device is a leaf that opens straight into its
target card, where Service identity stays. A managed Network's own
administration detail is reached from its root; a Network merely observed
offers none, because Discovery is not authority.

Scan, Inspect and Analyze remain distinct observation roles rather than stages
of a mandatory pipeline, and manual Inspect is optional technical depth rather
than a target stage. Inspect is also how a target gains a name: a remembered
Device is an unknown Device at its observed address until an Inspect legitimately
observed its represented display name. Remembered positive observations live in
Discovery; deeper learned information lives in Knowledge; established access is
a persistent `DeviceAccess` relationship, and an active Remote Session is a
separate operating context over it. NodeScan presents all reconnaissance from
player information only, as one target at a time with its technical depth
progressively disclosed. Represented server Devices keep their own bounded
Authentication History.

Details: [`current/NETWORK_ACCESS.md`](current/NETWORK_ACCESS.md).


## VEYRA OS — the foreign personal phone

One represented ordinary personal phone, `Petra’s Phone`, sits on the player's
own `home-net` and is reached through exactly the loop above: it runs the same
represented vulnerable SSH release as `srv-01` and needs the same Knowledge and
the same tool. Entering it mounts VEYRA OS, a foreign consumer Firmware surface
that reads as somebody else's ordinary smartphone rather than as another
machine console.

Its Home is a conventional app launcher whose entries are derived from
represented truth: Wallet, because that Device has a Civic Dollar Financial
Session, and Settings, because it has represented Firmware. Communication is
absent rather than faked, because no foreign communication truth is
represented. Wallet is a second client over the same canonical Dollar domain
and can really send money from that phone's Account; Settings presents the
Device name and system version, plus a Security surface where changing the
phone's Wallet-protection setting requires the Device's own PIN. The player's
Remote Session never appears as the phone's own connection state and grants
no authority to change that PIN-gated setting.

Settings also exposes **System Update**, the phone's own Firmware capability:
it truthfully states the release the Device runs and the one concrete newer
official release VEYRA offers it, VEYRA OS 4.2. Installing requires the
Device's own PIN, runs as a real represented transition the phone advances by
itself through downloading, preparing, installing and restarting stages behind
a dedicated VEYRA installation surface, and ends with the Device actually
owning the new release — a visibly more refined VEYRA, and a phone whose
firmware-owned SSH implementation has moved to GateSSH 1.3.3. Firmware is not
software: nothing is downloaded, bought or installed as a package.

## Communication and mail

The player has a represented in-world mail account (`user@node.mail`) whose
mailbox is canonical `GameState`. It belongs to that mail identity rather than
to the local Device or NODE-OS; NodeMail is the NODE-OS client onto it, and
Home derives an unread count from canonical mail state.

Two authored threads exist: a read-only NodeMail account notice, and one
interactive first-contact correspondence with Myra Keller. In that thread the player writes a
reply in their own words and a concrete authored rule produces a deterministic
answer — including the first VEYRA phone address when the player expresses clear interest.

What a correspondent said is historical snapshot content. Mail creates no
Discovery, Knowledge or access: a communicated address is a claim, and
verifying it remains the existing observation systems' job.

## Files, transfer, and software

Each represented Device owns its own canonical filesystem with six explicit
file kinds: text, software package, software module, the `deauth.ext` Flipper
Extension, executable, and the RATTLER payload. Remote-to-local Download
and local-to-remote Upload run as one canonical `FileTransfer` — real elapsed
network runtime that is not a `GameProcess`. A supported package that exists on
the local filesystem can be installed through Files or Terminal, which admits a
finite Software Installation Process; Software Removal is the corresponding
finite operation, started from System's inline installed-software management.
NODE Miner is the one represented runnable program: installation creates its
executable, and RUN admits it as a continuous Process — on the local Device, or
on the Device currently operated through RACK-OS.

The player starts with a standalone Credential Access Module artifact that
directly provides the first Technique, while Flipper is acquired and installed
later from the Market and opened through its concrete executable in Files. The
current module artifacts are standalone Technique providers and compatible
Flipper integration inputs; "module" is current host/product terminology, not
the universal category for an offensive capability. A module artifact is never
installed: integrating one is finite local work that transforms the installed
Flipper into a different build of the same release — a distinct build identity,
a larger represented size, and one more integrated module — while the source
artifact remains an ordinary owned file. Capability comes from the represented
standalone artifact or integrated module state, never from the build identity
being different.

Package, Module, InstalledSoftware, Executable, and Process remain five
distinct things.

Details: [`current/FILES_SOFTWARE.md`](current/FILES_SOFTWARE.md).


## Software Market

Software can be acquired for NODE. One represented broad/open Market, operated
by a represented party that is not NODE, lists six concrete offerings — five
packages (including Flipper) and one Flipper module — at 0.01 NODE each, 10,000 canonical atomic
units, with truthfully mixed provenance and channel stated only where a release
actually represents them, and including the Rollback Module's first represented
acquisition path. A module offering distributes a module artifact rather than
an installable package; the operator remains the seller of its own broad/open
market, not an official NODE store.
Buying debits the local Wallet
and credits that operator's own NODE account atomically and establishes a
canonical entitlement identified by offer identity; it creates no file and
installs nothing. A purchased offering can then be downloaded as a real
canonical `FileTransfer` from the Market's own distribution endpoint — a second
admitted transfer origin authorized by the entitlement rather than by
DeviceAccess — and the ordinary package artifact appears on the local Device
only when that transfer completes. Entitlement and physical possession stay
separate truths, and the Market ends at acquisition: installation remains
Files' job, and integrating a module remains Flipper's.

Details: [`current/MARKET.md`](current/MARKET.md).


## Processes and activity

Processes represent elapsed work and resource consumption on a concrete
executor Device. Current consumers are Service Analysis, Credential Access,
Software Installation, Software Removal, Flipper Module Integration, and the
continuous NODE Miner;
Software Installation and NODE Miner execution may run on a represented remote
Device, using that Device's own CPU and RAM. The
Processes application is presented as the NODE-OS Activity Monitor, which
derives one view over canonical Process state and the single canonical active
FileTransfer without merging those runtime domains, and retains bounded Recent
Activity history.

Details: [`current/PROCESSES_ACTIVITY.md`](current/PROCESSES_ACTIVITY.md).


## Dollar finance, NODE economy and Wallet

NODE is represented as canonical integer atomic units. A running NODE Miner
produces NODE from its actual allocated compute and routes completed batches to
represented economic recipients by exact address match; the unofficial NODE
Miner 1.0 release additionally diverts a share to its own embedded address. A
running Miner's payout address can be retargeted in place from the RACK-OS
Terminal without stopping it, and its Device-owned payout log records one line
per payout routing segment so earlier payouts stay attributed to the address
that actually received them.

Dollars move for the first time. One immediate transfer operation debits a source Account and credits a recipient Account atomically and appends exactly one canonical Transaction; its source Account is derived from the acting Device's Financial Session rather than supplied, and it fails closed without mutating anything when the Session, recipient, amount or balance does not hold. Account activity is derived from those Transactions and keeps the counterparty reference each transfer actually used.

Wallet leads with a Dollar client — a balance hero with the account reference and a trajectory across represented Transactions, then SEND, RECEIVE and ACCOUNT, then activity, all for the Account the local Device's Financial Session resolves — and presents NODE beneath it as a separate, secondary economic system. The Device stores its own saved sign-in, distinct from the Provider's Credential, so the player normally continues into their personal Account without retyping a password, while manual sign-in remains available for any other Account and signing out is reversible.

Details: [`current/DOLLAR_FINANCE.md`](current/DOLLAR_FINANCE.md) and [`current/NODE_ECONOMY.md`](current/NODE_ECONOMY.md).


## Not currently implemented

The following are not current implementation truth:

- filesystem writes
- filesystem permissions
- general remote execution, arbitrary program launch, or a remote shell
- remote Process observation surfaces
- per-application access permissions
- privilege escalation
- generalized exploit systems
- broader hacking mechanics
- reachability simulation
- firewall simulation
- malware simulation
- autonomous actors
- systemic authorities
- simulation-time world change
- economy simulation
- organization simulation
- multiplayer
- authoritative backend
- real networking
- saves
- migrations

Three entries previously listed here — remote filesystem access, a foreign
Remote Session operating surface, and foreign operable Firmware — were removed
during the V1 knowledge migration because current accepted `main` implements
them as RACK-OS (see [`current/NETWORK_ACCESS.md`](current/NETWORK_ACCESS.md)
and [`current/FILES_SOFTWARE.md`](current/FILES_SOFTWARE.md)); a second foreign
Firmware surface, VEYRA OS, is now implemented alongside it (see
[`current/VEYRA_OS.md`](current/VEYRA_OS.md)). See
[`MIGRATION_NOTES_KNOWLEDGE_V1.md`](MIGRATION_NOTES_KNOWLEDGE_V1.md).

Three further entries — remote execution, remote Processes, and remote compute —
were narrowed for the same reason: remote Software Installation and remote NODE
Miner execution both run real Processes on a represented remote Device's own
CPU and RAM. What remains unimplemented is the general case listed above.

Future direction for unimplemented systems belongs to
[`docs/FUTURE.md`](FUTURE.md).

Planned work does not become current truth until it has been implemented,
reviewed, accepted, and integrated.
